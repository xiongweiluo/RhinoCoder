## 已核实的结论

冻结的 GPU 解释器 `/data/conda-envs/rhinocoder/bin/python3.11` 缺少 `os.pidfd_open`，但具备 `os.fork` 与 `signal.pidfd_send_signal`。归档 `supervise()` 第一条语句要求 Linux 及三种原语同时存在；当前解释器的这条门禁将拒绝 `reuse_linux_owned_child_primitives`，发生在日志、准入登记、fork 和 worker 启动之前。本次仅复算该谓词并核实源码位置，没有调用 `supervise()`、打开 pidfd、发送信号或运行模型。诊断允许只读 SSH、`sysctl` 和 `nvidia-smi` 子进程；作用计数中的 fork 指研究 supervisor 所有的 worker 创建，不宣称检查完全没有操作系统子进程。

这个确定的当前阻塞与 C 缺少 GPU supervisor/worker/准入记录的现场现象一致。**C 原远端 stderr 已被丢弃，本次没有重放原入口，因此不能追认证明 C 当时唯一异常就是此门禁。** 原 controller EOF、独立停止失败、有限宿主收尾、工程门失败和永久退休记录完整保留，见[原失败报告](c5-reuse-development-startup-failure-20261012-c.md)。

机器证据在[只读诊断记录](../eval/c5/reuse-c-startup-readonly-diagnosis-20261012.json)。记录包含实际观察时间、诊断源码 SHA、原失败记录 SHA、两个原始 stdout 的 SHA 和消费快照；没有私题、答案、key 或实际模型输出。完整已安装环境和模型字节本轮未重哈希，过去原 `--serve` argv/退出 stderr 未重建。读取的是既有公共冻结和限定退休/准入元数据；没有读取正式 holdout 或私有审计密钥。

## 同时发现的后续工程缺口

1. 旧预检能验证冷导入、字节、权限和资产，却未覆盖真实入口第一原语门禁，也不能用诊断进程 argv 证明实际 serve 调用身份。后续预检必须在将来实际解释器和权限路径上覆盖新入口的无作用前段，并明确诊断身份与执行身份的差别。
2. 归档 `supervise()` 使用 `AdmissionRegistry(binding)`，默认 `create=False`；GPU 原目录缺席将形成后续初始化阻塞。此位置晚于第一原语门禁，不把静态缺口写成已发生的历史异常。更不能直接添加 `create=True` 绕过已消费 Mac 记录和原跨目录一次性规则。
3. 旧 controller 异常路径先调用独立停止，只有返回后才进入已知原生收尾；停止抛错会跳过首次已知 hub 收尾。新 CPU 原型分别记录两个回调结果，使停止异常不能跳过这次收尾；二者仍各至多一次，失败不追加停止或重放。
4. 旧 SSH 将 stderr 送到 `DEVNULL`，失去原始失败原因。新 CPU 原型保留至多 262144 字节前缀，同时继续观察流、累计总长度与全部已观察字节 SHA。截断、缺 EOF 或缺退出状态不得宣称完整原始捕获；任何捕获都不独自产生执行成功、资格释放或重试权限。

这两个原型 **没有接入旧现场入口**。其 CPU 回调为合成对象；还没有实现真实 SSH 并发排空、超时/终止生命周期、耐久文件和原始联合审计绑定。批准准备后必须实现并检验这些内容，再冻结。没有以整数 PID 或按名称 kill 代替原生 pidfd 契约，也没有切换到系统 Python 运行研究。
