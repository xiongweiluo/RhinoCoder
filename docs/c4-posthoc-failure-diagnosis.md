# C4 事后失败诊断（只读）

日期：2026-09-21。结论：**维持 C4 `NO-GO` 与现有混合路由；目前不启动 dataset v2、第二轮训练或 GPU 租赁。** 本文是事后解释和评测合规性补充，不修改 C0 预注册、C3 一次性 A5、P2 冻结协议、既有原始结果或 C4 计分。

## 核查范围与可复现性

只读取锁定 train 210 条、validation 45 条、公开的 C2/C4 汇总、固定 Qwen tokenizer、当前 23 个 MCP 工具定义，以及 Git 忽略目录中的既有 P2 base/LoRA 原始记录。脚本先核对 train/validation 与 C0 配置 SHA-256、P2 协议与公开 C4 的 SHA-256、两路 P2 原始文件与公开 C4 的 SHA-256、每路恰好 30 个有效任务槽。它只打印聚合计数，不输出样本、提示、模型原文、Rhino GUID 或任务 ID：

```bash
python tools/diagnose_c4_failures.py
```

没有打开或再次运行 A5 holdout，没有模型推理、Rhino 操作或 GPU 工作。固定 tokenizer revision 为 `c03e6d358207e414f1eca0bb1891e29f1db0e242`；训练最长序列为 2,048 token。[C2 报告](c2-qlora-training-report.md)记录了 train loss 0.9167、validation loss 0.7503，但 validation 四个结构化工具指标均为 0；当时的三样本只读探针也没有结构化命中。Loss 下降不能替代端到端工具调用能力。

## 发现：按证据强度排序

| 顺位 | 发现 | 直接证据 | 解释边界 |
|---|---|---|---|
| 1 | **训练与实际推理的输入契约不同** | 训练和 C2 validation 生成均未向 Qwen chat template 传入 `tools`；P2 推理服务向同一固定模板传入 Agent 的 23 个工具 schema。以锁定 train/validation 提示作受控 tokenizer 重渲染，附加工具 schema 使提示中位数分别由 132/99 变为 13,239/13,206 token；255/255 都超过训练上限 2,048。 | 这是确定的分布差异，**不是**直接测量 P2 实际上下文，也不能单凭 token 差异证明失败因果；P2 还会加入不同的系统提示。不得把 2,048 误写成推理模型的上下文上限。 |
| 2 | **失败首先集中在未形成工具调用** | P2 的 base 与 LoRA 均有 20/30 个有效任务以零工具调用失败，且均到 `agent.max_rounds`。失败标签中的空间、感知、恢复等多数都落在这 20 个零工具调用任务里。训练目标本身经固定模板重渲染后，train 210/210、validation 45/45 都可被既有结构化解析器准确还原。 | 目标序列化/解析器对*标准答案*有效；并不说明模型生成也合格。零调用可能来自自然语言、错误标签/JSON、未完成输出或控制器交互；仅凭聚合记录不能再细分，也不能把这些任务直接判作 Rhino 几何执行失败。 |
| 3 | **监督覆盖远窄于生产工具面** | train 目标仅出现 6 种工具，validation 仅 5 种；运行时 Agent 提供 23 种工具。train 中 155/210、validation 中 35/45 的 assistant 目标同时包含自然语言内容。 | 说明数据覆盖与输出风格值得检查，但不足以证明自然语言内容本身导致零解析；也不能据此宣称某个新数据配比一定有效。 |
| 4 | **下游能力错误尚难归因** | 有效结果按任务断言的失败标签：base/LoRA 的空间各 7、感知各 5、恢复各 5、规划各 2、隐私各 1；澄清为 6/5。两路各 20 个零调用失败覆盖空间 7、感知 5、恢复 5、规划 2、隐私 1。 | 标签描述最终任务未满足的类别，不等于工具被调用后真实几何、感知或恢复算法失败。应先解决能否稳定产生合法工具调用，再归因下游。 |

### 冻结 P2 的评测合规性限制

[P2 comparison protocol](../eval/p2/model-comparison-protocol.json)写明每个任务每路 1 次尝试；在首次模型/工具结果前的基础设施故障，同槽最多补位一次。base 原始记录 36 行，其中 6 次基础设施中断，分属 6 个任务，每个 1 次；其余 30 个有效任务槽。LoRA 原始记录 74 行，其中 44 次基础设施中断、30 个有效任务槽；**15 个任务有超过 1 次基础设施中断**（13 个有 2 次，2 个有 3 次）。现有 C4 汇总器核查“每任务恰好一个有效结果”，但没有强制“最多一次基础设施补位”，因此没有报告这项偏差。

这些中断记录均无工具调用，Rhino scene before/after 也均未变化；其中 2 条 LoRA 记录的 fixture 故障注入剩余计数发生设置变化。故不能简单断言“绝无状态影响”。已公布的 base 4/30、LoRA 5/30 和配对统计是**原始记录的描述性结果**；LoRA 路不应再被描述为完全符合冻结重试规则的严格 Pass@1 证据。不能事后删掉多余记录、重跑 P2 或重新定义规则来修复该偏差。这个限制不把 `NO-GO` 变成 `GO`：A5 一次性配对两路均为 0/45，P2 描述性差值也只有 +3.3pp、净胜 1，均未达到既定门槛。

## 下一步决策

1. **维持已验证的混合路由，不将本地 LoRA 设为产品默认模型。** 混合路由先前在 P2 上为 18/30，但系统/模型配置与本次 base/LoRA 配对不同，不能将 18/30 解读为单一基座模型更强。
2. **先做无 GPU 的契约设计与合成测试。** 明确训练、validation、P2/live inference 共同采用的 system prompt、工具 schema 的呈现/裁剪策略、`<tool_call>` 序列化与解析契约；用合成样本检验解析、工具名/参数和 2,048 token 内可训练性。任何新设计只用于*下一实验*，不可回写本次冻结结果。
3. **只在契约稳定后评估 dataset v2。** 若合法工具调用仍是瓶颈，再针对合法调用、澄清、感知、恢复和几何闭环收集高质量示例，先审覆盖与质量，再谈训练。必须新实验 ID、新预注册、新的未见保留集；已消费的 A5 和这套已分析的 P2 不能成为调参/挑模型的盲测。一次只改变一个主要因素，避免同时更换基座和数据/LoRA 配置。

因此，“是否值得现在启动 dataset v2”的答案是**暂不**。最便宜且最可判别的前置工作是冻结一份统一工具调用契约，并用合成数据验证；若它不能以合理长度覆盖运行工具面，先改系统/协议设计，而不是追加训练预算。

后续已完成这一前置工作的[CPU-only 候选契约与合成预算核查](tool-call-contract-v2-candidate.md)：双阶段单工具方案在短合成输入下可行，但尚未接入控制器、真实推理或新实验，**不改变上述 dataset v2 暂缓决定**。
