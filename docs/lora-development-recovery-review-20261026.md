## 此次合并到同一执行链的内容

| 原工程问题 | 现在的统一规则 |
| --- | --- |
| 仓库测试能导入，实际分发包缺依赖；测试另补配置 | Mac控制入口和GPU角色入口的 `--check` 与正式入口共用 `prepare()`，从同一个包读取配置、公开依赖、schema和待执行计划。Rhino角色入口共用 `prepare_host()`；CPU检查不调用Rhino |
| 各端复制超时/剩余槽计算；环境审核本身触发延迟导入 | 超时和恢复语义集中在 `lora_development_runtime.py`，包中固定该配置；租期窗口按31个实际待执行槽计算。模块来源审核只读已经存在的模块字典，重复审核不执行延迟加载属性 |

| 一个may_advance同时限制任务接续和反馈选择；首槽失败封死整批 | 原首槽结果完整引用，另附已审核的“0请求/0夹具且清理完成”恢复依据；新执行只开放01–31。任务成绩、是否能安全继续、反馈选择资格分别处理 |
| 新批次容易形成新计数和新审批 | 仍用同一全局campaign根、原初始化标记与永久claim，只追加新策略和版本记录，不重建账本。一次确认范围，版本变化只做技术核验；超过语义边界才集中再批 |

## 接续和停止只有以下几类

| 事件 | 动作与保留结果 |
| --- | --- |
| 任务正常完成、拒绝或任务失败，回执/效果与清理已核实 | 如实评分，继续下一未尝试槽；不会因失败成绩停止或改题 |
| 模型请求前的局部夹具验证不匹配，宿主仍健康，清理和证据完整 | 该槽永久记工程失败，不补跑；同一活跃运行内继续下一槽 |
| 槽开始前的准备检查失败 | 在永久槽claim之前停止，未尝试槽不被消费；保留失败原因与收尾 |
| 模型响应未知、协议/身份/源码/证据异常、原生效果或清理未知、超时、用户中断 | 停止新工作，按已授权范围清理、导出、审核和不完整报告。未知不伪装成模型质量失败；不在状态未知时继续 |
| 新版在GPU启动前失败 | 只有“GPU未尝试启动、无新增槽、清理已核实”且有针对性源码修复时，才能在同一授权内经CPU/CI/完整性核验改版接续；原失败仍保留 |
| 第5次加载已经消费后再次整批中断 | 现有额度用尽，停止、收尾与分析；本方案不授权自动重载恢复余槽。以后增加加载或改变停止语义须集中确认，不将其伪装为普通启动修复 |

这次允许从已审核第4次停止点继续31槽，并允许同一次健康运行跨过可确认的局部工程失败；它不承诺任何中断都可无条件恢复。保留失败与不重放，与继续尚未尝试任务是独立规则。

## 自行处理与再次确认的边界
